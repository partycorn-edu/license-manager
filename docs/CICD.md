# CI/CD на GitHub Actions

Файл пайплайна: `.github/workflows/ci.yml`.

## Что происходит

| Шаг | Когда | Что делает |
|---|---|---|
| test | push и pull request | `ruff`, `pytest`, сборка фронтенда |
| build | после test | собирает 4 образа (api, auth, worker, gateway) через buildx. На push публикует в приватный GHCR с тегами `latest` и короткий sha. На pull request только собирает, не публикует |
| smoke | после test | поднимает полный compose-стек, проверяет `/healthz`, `/api/health`, `/auth/health`, вход и дашборд, 401 без токена, что postgres не опубликован, что Prometheus видит цели. Потом всё удаляет |
| deploy | только push в main, после build и smoke | по SSH копирует файлы стека на VPS, делает `docker login`, запускает `scripts/deploy.sh`, проверяет, что сервисы поднялись |

Деплой входит в CI/CD. Образы для деплоя берутся с тегом sha именно этого коммита.
Вход в GHCR при сборке идёт через встроенный `GITHUB_TOKEN`, отдельный токен для публикации не нужен.

## Шаг 1. Приватный репозиторий и приватные пакеты

1. Создайте на GitHub репозиторий с видимостью Private и загрузите проект.
2. Первый push в main соберёт образы. Пакеты будут в разделе Packages вашего профиля.
3. Для каждого пакета (`lic-api`, `lic-auth`, `lic-worker`, `lic-gateway`) откройте Package settings и проверьте блок «Danger Zone, Change package visibility»: должно быть Private. Если стоит Public, переключите.
4. В Package settings добавьте репозиторий в «Manage Actions access» с правом Write, если сборка не может записать в пакет.

## Шаг 2. SSH-ключ для деплоя

На своём компьютере (PowerShell):

```powershell
ssh-keygen -t ed25519 -C "github-deploy" -f $HOME\.ssh\licenses_deploy
```

Пароль на ключ не задавайте (Enter), иначе Actions не сможет им пользоваться. Появятся два файла: `licenses_deploy` (закрытый, в GitHub) и `licenses_deploy.pub` (открытый, на сервер).

На сервере под пользователем `deploy`:

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
nano ~/.ssh/authorized_keys     # вставьте строку из licenses_deploy.pub
chmod 600 ~/.ssh/authorized_keys
```

Ограничение прав ключа. Допишите в начало строки в `authorized_keys` опцию `restrict`:

```
restrict ssh-ed25519 AAAA... github-deploy
```

`restrict` запрещает проброс портов, агент и графический режим. Команды выполнять можно, они нужны деплою.
Дополнительно:
- ключ принадлежит отдельному пользователю `deploy`, а не root;
- этот ключ нужен только для этого проекта;
- помните, что членство в группе docker даёт доступ уровня root. Самая сильная защита здесь это сохранность секрета `VPS_SSH_KEY`.
Вход по паролю отключить стоит отдельно в `/etc/ssh/sshd_config` (`PasswordAuthentication no`), но делайте это только когда ключ уже проверен, иначе потеряете доступ.

Строка с отпечатком сервера (для защиты от подмены):

```powershell
ssh-keyscan -p 22 ВАШ_IP
```

Скопируйте вывод целиком, он пойдёт в секрет `VPS_KNOWN_HOSTS`.

## Шаг 3. Токен на чтение образов

Сервер скачивает приватные образы, поэтому ему нужен токен.

1. GitHub, Settings, Developer settings, Personal access tokens, Tokens (classic), Generate new token (classic).
2. Отметьте только `read:packages`. Больше никаких прав.
3. Срок: подберите (например 90 дней) и запишите, когда его менять.
4. Скопируйте токен, он показывается один раз.

Классический токен нужен потому, что для пакетов GHCR точечные (fine-grained) токены не подходят.

## Шаг 4. Секреты и переменные в GitHub

Репозиторий, Settings, Secrets and variables, Actions.

Secrets:

| Имя | Что положить |
|---|---|
| `VPS_HOST` | IP или имя сервера |
| `VPS_USER` | `deploy` |
| `VPS_SSH_KEY` | содержимое закрытого ключа `licenses_deploy` целиком, с первой и последней строками |
| `VPS_KNOWN_HOSTS` | вывод `ssh-keyscan` из шага 2 |
| `VPS_SSH_PORT` | номер порта SSH, если не 22 (иначе можно не создавать) |
| `GHCR_READ_USER` | ваш логин GitHub |
| `GHCR_READ_TOKEN` | токен `read:packages` из шага 3 |

Variables (вкладка Variables):

| Имя | Что положить |
|---|---|
| `VPS_GATEWAY_PORT` | порт приложения на сервере, например `8088` |

Паролей приложения (БД, JWT, admin) в GitHub нет. Их создаёт на сервере `scripts/create-secrets.sh` как docker secrets.

Рекомендуется также включить защиту ветки main и окружение с ручным подтверждением, но это необязательно.

## Шаг 5. Запуск

Сделайте push в main. Откройте вкладку Actions, там будет запуск «CI/CD» с четырьмя шагами.
Ожидание: все шаги зелёные, в конце deploy видны строки `OK /healthz`, `OK /api/health`, `OK /auth/health`.

Pull request проходит test, build (без публикации) и smoke, но не деплоит.

## Нагрузка на VPS при деплое

Предупреждение: во время деплоя Docker скачивает образы и пересоздаёт контейнеры. На сервере с 300 МБ свободной памяти это самое рискованное место.
Что уже сделано:
- образы собирает GitHub, на сервере ничего не собирается;
- обновление идёт по одному сервису (`parallelism: 1`), поэтому одновременно пересоздаётся только одна копия;
- после деплоя старые образы удаляются.
Что стоит сделать:
- держать включённый своп (см. [VPS.md](VPS.md));
- деплоить в тихое время.

## Откат

Автоматический: если новая версия сервиса не стала healthy за время `monitor`, Swarm сам откатывает этот сервис (`failure_action: rollback`), а `deploy.sh` завершается с ошибкой, и шаг deploy в Actions красный.

Вручную, на предыдущую версию, на сервере под `deploy`:

```bash
cd ~/licenses
cat .deploy-history          # список задеплоенных тегов, последний внизу
sh ./scripts/rollback.sh     # откат на предыдущий тег
sh ./scripts/rollback.sh abc1234   # откат на конкретный тег
```

Ожидание: скрипт выполняет полный деплой с выбранным тегом и выводит `Деплой abc1234 завершён успешно`.
Откат на один шаг для одного сервиса средствами Swarm: `docker service rollback lic_api`.
Откат кода через Git: сделайте `git revert` плохого коммита и запушьте в main, CI соберёт и задеплоит исправленную версию.
Образы старых версий остаются в GHCR по тегам sha, поэтому откат возможен, пока вы их не удалили.

## Частые ошибки

| Симптом | Причина и решение |
|---|---|
| `Permission denied (publickey)` | неверный `VPS_SSH_KEY` или открытый ключ не добавлен на сервер, либо лишние пробелы и обрезанные строки в секрете |
| `Host key verification failed` | неверный `VPS_KNOWN_HOSTS` или не тот порт в `ssh-keyscan` |
| `denied` или `unauthorized` при docker login | токен без `read:packages`, неверный логин или токен истёк |
| `manifest unknown` на сервере | образ с этим sha не опубликован: шаг build не выполнялся или это pull request |
| build: `denied: permission_denied` | у пакета не включён доступ репозитория (шаг 1, пункт 4) |
| smoke: `Сервисы не поднялись` | смотрите шаг «Логи при ошибке» в Actions |
| deploy зелёный, но сайт не открывается снаружи | порт закрыт в firewall хостинга. Проверьте `VPS_GATEWAY_PORT` и правила |
| deploy: `ОШИБКА: сервисы не поднялись за 300 сек` | не хватает памяти или не скачался образ. На сервере: `docker stack ps lic --no-trunc` и `free -m` |
